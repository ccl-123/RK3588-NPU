# 开发者文档

> 版本: v2.4
> 更新日期: 2026-04-01

## 开发环境

- 硬件：RK3588 系列开发板，如 EC-A3588Q、Rock 5B、Orange Pi 5
- 操作系统：Ubuntu 22.04
- 编译器：GCC / G++ 11.4+
- 构建工具：CMake 3.14+
- 关键依赖：
  - Qt 5.15+
  - OpenCV 4.x
  - SQLite3
  - RKNN Runtime
  - RKLLM Runtime
  - Rockchip MPP Runtime (用于硬件解码 MJPEG)
  - Rockchip RGA (用于硬件色彩转换、缩放、翻转与填充)
  - spdlog / fmt

## 工程结构

```text
C++/face_recognition_cap/
├── include/
│   ├── agent/          # ReAct Agent、工具执行、对话记忆
│   ├── app/            # 应用编排、模型管理、RKLLM 线程
│   ├── core/           # YOLO / FaceNet 核心算法封装

│   ├── gui_services/   # AI / 天气 / 新闻 / 节假日等 GUI 服务
│   ├── gui_utils/      # GUI 工具类
│   ├── hardware/       # 摄像头与硬件抽象
│   ├── service/        # AttendanceService / UserService
│   └── tools/          # Agent 工具集
├── src/
├── gui/
├── data/
├── docs/
├── build.sh
└── cross_build.sh
```

## 构建方式

### 板端直接构建

```bash
cd C++/face_recognition_cap
./build.sh
```

### 交叉编译

```bash
cd C++/face_recognition_cap
./cross_build.sh --build
```

说明：

- `./build.sh` 更适合板端本地开发
- `./cross_build.sh --build` 更适合 PC -> RK3588 的交叉构建

## LLM 接入方式

当前项目支持 2 种大模型路径：

### 1. 本地 RKLLM

```bash
export LOCAL_LLM_MODEL_PATH=/path/to/your_model.rkllm
```

### 2. OpenAI 兼容远端接口

```bash
export LLAMA_CPP_SERVER_URL=http://127.0.0.1:8080
export LLAMA_CPP_SERVER_MODEL=gpt-4o-mini
export LLAMA_CPP_SERVER_API_KEY=sk-your-key
```

说明：

- 远端模式通过 `LLAMA_CPP_SERVER_URL` 调用 OpenAI 兼容接口
- 代码会自动拼接 `/v1/chat/completions`
- 变量名保留 `LLAMA_CPP_*` 历史前缀，但后端不要求必须是 llama.cpp

详见：

- [OpenAI兼容接口接入说明.md](./OpenAI兼容接口接入说明.md)

- `lookup_attendance_ranking`

- `calculator`

这些工具统一由：

- `ToolRegistry`
- `ToolExecutor`
- `ReactAgent`
- `AgentService`

串起来工作。

## 新增工具时不要漏改

新增 Agent 工具时，不要只写 `.cc` 和 `.h`，至少还要同步改：

1. `AgentService::registerBuiltinTools()`
2. `CMakeLists.txt`
3. `system_tool.cc` 中的 `HelpTool`
4. `PromptTemplates`
5. 相关开发文档 / 用户文档 / README

否则会出现代码里已经有工具，但模型提示词和帮助里不知道它存在的漂移问题。

## 数据库与业务层

核心业务类：

- `AttendanceService`
- `UserService`

常见 DAO：

- `AttendanceRecordDAO`
- `UserDAO`
- `FaceFeatureDAO`

新增的部门、排行、缺卡工具都依赖：

- `users`
- `attendance_records`

因此如果以后要继续增强 Agent，优先考虑复用现有 `Service` 层，不要直接在工具里写原始 SQL。

## 调试建议

- 算法与推理链路：看 `spdlog::debug`
- 远端请求问题：优先看 `AiAnalysisService`
- 本地模型问题：优先看 `LocalAiAnalysisService` 与 `LocalLLMThread`
- 工具选择问题：优先看 `PromptTemplates`、`ToolExecutor`、`Agent模块说明.md`

## 零拷贝与多硬件加速设计 (MPP & RGA & RKNN)

为了追求极致的性能与最低的 CPU 资源占用，项目对视频采集、解码、图像预处理以及 NPU 推理链路进行了完全重构：

### 1. 热路径硬件加速设计 (V4L2 → MPP → RGA → RKNN NPU)
* **采集层 (V4L2)**：直接执行 `DQBUF` 抓取 MJPEG 原始压缩码流包，不调用 CPU 做任何图片解码，实现极速码流获取。
* **硬件解码 (MPP)**：使用 MPP 任务模式 (Advanced Task API)，压缩 MJPEG 输入通过 `mpp_buffer_write()` 写入 MPP 输入缓冲；输出配合应用级分配的 DRM/NV12 帧，由 MPP 硬件解码并通过 `mpp_buffer_get_fd` 导出共享文件句柄 `decoded_fd` (dma-buf fd)。
* **硬件预处理 (RGA)**：将 `decoded_fd` 传入 RGA，由 RGA 硬件芯片一气呵成处理 **NV12颜色转换 + 水平镜像翻转 + 缩放 + Letterbox补黑边** 并直接写入绑定的 NPU 输入物理内存，实现像素在整个主推理通道中 **Zero CPU Copy**。
* **NPU 零拷贝推理 (RKNN)**：初始化时通过 `rknn_create_mem` 创建输入输出物理内存并执行 `rknn_set_io_mem` 永久绑定。推理时仅需调用极轻量的 `rknn_run`，完全消除 `rknn_inputs_set` 内存拷贝的开销。
* **多线程数据隔离机制**：主线程与预处理线程共享 NPU 输入内存，通过 `npu_mem_mutex_` 与 `cv_npu_input_` 确保互斥写入与推理消费。推理完成后，主线程在同步锁保护下快速拷贝输出数据（约 <0.1ms）后立即解锁，完美规避下一次预处理写入与后处理读取之间的数据竞态。

### 2. 降级边界
* **MPP 解码失败**：当前稳定路径直接丢弃该帧并继续下一帧，不再启用不稳定的 V4L2 dma-buf 压缩输入，也不声明 MJPEG 输入端零拷贝。
* **RGA 异常降级**：若 RGA 硬件预处理失败，则使用 CPU 完成 NV12 转换到 BGR，在 CPU 中执行水平翻转与缩放并直接写入绑定的 NPU 输入虚拟内存（`npu_input_mem_->virt_addr`）。
